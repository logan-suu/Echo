# ADR-005: 翻译质量兜底改为源语言检测置信度

**状态**: 已接受
**日期**: 2026-08-02
**决策人**: logan-suu（人类审批）+ Echo UI Agent

## 背景

US-DIS-002 AC-3 原文要求：

> 置信度 <0.7 保留原文 + 语言标签。

双语言实现文档 §6.4 同步要求「若端侧翻译置信度 < 0.7，保留原文 + 语言标签，不提供低质量译文」。

但在实现中发现该验收条件**技术上不可落地**：

- Apple Translation Framework（swift-translation，iOS 18+）的公开 API 只返回 `targetText` + `sourceLanguage`，**不提供任何译文质量/置信度分数**（`TranslationSession.Response` 无置信度字段）。
- 规格中的「翻译置信度」在现有技术栈下无法按字面实现，PR #43 中仅能以 fixture 合成值模拟，形成不可验证的验收条件。

## 决策

将「翻译输出置信度」（不可实现）重新定义为**源语言检测置信度**（可实现）：

- **信号来源**：NLTagger（iOS 18+，双语言文档 §6.2 语言检测契约）。
- **阈值**：< 0.9（与 §6.2 既有 NLTagger 置信度阈值 ≥ 0.9 对齐），低于阈值标记 `.uncertain`。
- **触发行为**：源语言检测不确定时，翻译方向（zh→en 还是 en→zh）不可靠 → **保留原文 + 语言标签，不提供译文**。

修订后 AC-3 语义：语言检测确定性作为**翻译方向可靠性**的代理信号——检测不确定时宁可退回原文，避免把方向译反的译文展示给用户。这保留了原 AC-3「质量兜底」的设计意图（不提供低质量译文），同时信号真实可测。

## 备选方案

| 方案 | 描述 | 结论 |
|------|------|------|
| **A（采纳）** | 改用源语言检测置信度（NLTagger <0.9） | ✅ 可实现、与 §6.2 契约对齐、保留质量兜底意图 |
| B | 保留合成「翻译置信度」概念，标注 🔮 待未来信号源 | ❌ 继续维护一个不存在的概念，AC 不可验证 |
| C | 用术语表命中率作为代理 | ❌ 仅覆盖术语片段，不覆盖一般翻译，覆盖面过窄 |
| D | 移除 AC-3 质量兜底 | ❌ 丢失降级透明性（§8.2 禁止静默返回低质量结果） |

## 后果

### 正面

- AC-3 变为可落地、可测试（NLTagger 检测确定性）。
- 与双语言文档 §6.2 语言检测契约（≥0.9 / `.uncertain`）概念统一。
- 保留「低置信度不展示译文」的用户保护意图。

### 负面

- 需同步修订：规格书 AC-3、双语言文档 §6.4/§8.1、UI 切片字段语义（`translationConfidence` → `sourceLanguageConfidence`）、契约与 fixture。
- 若未来 Apple 提供译文质量信号，可再引入独立于检测置信度的「译文置信度」。
